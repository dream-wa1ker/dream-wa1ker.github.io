NAME

watching my own TCP handshake in Wireshark

2026-07-28 c sockets wireshark

Setup

I know wireshark as a tool when I first installed kali linux out of curiousity like a cashew. Guess this is the right time to do it. SYN, SYN-ACK, ACK - three basic network replies that determines the connection between two or more devices that are connected in the Internet.

This is basically the TCP/IP stack - and I am just beginning to understand it. To simply understand it by your own, you need to write a simple client server model in C via sockets : AF_INET, as I have shown below.

The server

Nothing to worry about - socket(), bind(), listen(), accept(). The interesting part is what each call actually triggers at the kernel level:

server.c 

int sockfd = socket(AF_INET, SOCK_STREAM, 0);

struct sockaddr_in addr = {
    .sin_family = AF_INET,
    .sin_port = htons(8080),
    .sin_addr.s_addr = INADDR_ANY
};

bind(sockfd, (struct sockaddr *)&addr, sizeof(addr));
listen(sockfd, SOMAXCONN);

int client_fd = accept(sockfd, NULL, NULL);
// accept() blocks here until the three-way handshake
// has already completed - by the time this returns,
// the kernel has done SYN / SYN-ACK / ACK for you.

Wireshark output :

Those three packets are what going on irl:

capture (lo0, filtered on tcp.port == 8080) 

1  0.000000  127.0.0.1 -> 127.0.0.1  TCP  SYN     seq=0
2  0.000031  127.0.0.1 -> 127.0.0.1  TCP  SYN,ACK seq=0 ack=1
3  0.000052  127.0.0.1 -> 127.0.0.1  TCP  ACK     seq=1 ack=1

The most annoying part to understand: accept() doesn't do the handshake, the kernel already finished it before accept() returns anything. accept() just pulls a completed connection off the queue.

the socket API's job is to make three packets and a queue in the kernel look like a single function call - which is the kind of stuff worth breaking open once
